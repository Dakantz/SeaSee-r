# 3D Ocean Floor Mapping Roadmap

## Overall Goal
Create a 3D map of the ocean floor based on data collected from an ROV.

## Input Data
1. **Video:** Footage recorded by the ROV.
2. **Positional Log Data:** JSON-formatted data streams containing depth, attitude, and sonar metrics. Example:
    ```json
    [
        {
            "type": "depth",
            "time": "2026-05-05 11:48:29",
            "timestamp": 1777974509954,
            "payload": {
                "depth": 0,
                "temperature": 23.37
            }
        },
        {
            "type": "attitude",
            "time": "2026-05-05 11:48:29",
            "timestamp": 1777974509954,
            "payload": {
                "yaw": 324.3104,
                "roll": 9.347046,
                "pitch": 0.62719727
            }
        },
        {
            "type": "sonar",
            "time": "2026-05-05 11:48:29",
            "timestamp": 1777974509954,
            "payload": {
                "distance": 0,
                "altitude": -1,
                "left": 0,
                "right": 0
            }
        }
    ]
    ```

## Pipeline Steps

### 1. Data Preprocessing & Synchronization
- **Objective:** Parse the JSON log data to extract depth and attitude (orientation) streams, and sync these with the video frames.
- **Evaluation:** Relying on GPS underwater is unrealistic. The log data provided does not contain GPS (Lat/Lon) but rather depth and attitude. Therefore, instead of a GPX file, we should generate a local trajectory file (e.g., TUM or KITTI format) containing Timestamp, Depth (Z-axis), and Orientation (Pitch, Roll, Yaw).
- **Implementation Idea:** 
  - Extract the start time of the video from its metadata and align it with the JSON log timestamps.
  - Interpolate the 1Hz/2Hz log data to match the video frame rate (e.g., 30fps).

### 2. Keyframe Extraction & Quality Assessment
- **Objective:** Underwater video is often plagued by motion blur, marine snow, and featureless regions (e.g., open water or plain sand).
- **Implementation Idea:** Before running heavy SLAM or SfM, implement a lightweight script to parse the video and extract only high-quality keyframes. 
  - Use image processing metrics (e.g., Variance of Laplacian for blur detection, ORB feature count for texture richness).
  - This step outputs a curated set of frames that act as ideal control images for `openFsM` and reduces the computational load for the pipeline.

### 3. Constrained SLAM (Movement Approximation)
- **Objective:** Process the curated keyframes through a SLAM algorithm (like `pyslam`) to solve for the missing X and Y translations.
- **Implementation Idea:** 
  - **Fusing Log Data:** Feed the interpolated depth (Z) and attitude (orientation) data directly into the SLAM back-end as strict priors. This heavily constrains the optimization problem, massively reducing the typical drift and relocalization errors seen in underwater visual SLAM.
  - **Sub-mapping (Snippets):** If tracking is lost, save the current trajectory map as a localized "snippet" and initialize a new one. The output will be a set of unconnected but internally consistent local trajectories.

### 4. 3D Map Construction (`openFsM`)
- **Objective:** Construct the final dense 3D map of the ocean floor.
- **Implementation Idea:** 
  - Feed the curated keyframes into `openFsM`.
  - Crucially, use the trajectory snippets generated by the SLAM pipeline as **camera pose priors** in `openFsM`. This gives `openFsM` a massive head start, preventing it from failing during the sparse reconstruction phase and ensuring the scale of the 3D map matches the real-world depth data.
